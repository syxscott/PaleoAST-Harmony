# 散点/折线/直方图/柱状图的热力图与 EPS 几何抽成纯 TS 模块：画布与 SVG 导出共用一份

## 类型

缺陷修复 / 重构

- 散点 / 折线 / 直方图 / 柱状图：**重构，行为零变化**（逐位等价）
- 热力图：**缺陷修复**（导出图与屏幕图本来不是同一张图）
- EPS 导出：**重构，行为零变化**（逐位等价）

## 问题

2026-10-19 的全仓审查发现箱线图有**两套实现**（画布一套、SVG 导出一套），
修法是抽出 `plot/boxGeometry.ts`（纯函数）让两者共用。**同一类缺陷还留在**
散点、折线、直方图、柱状图、热力图上，EPS 导出里还有散点几何的**第三份拷贝**。

### 1. 散点 / 折线 / 直方图 / 柱状图

| 图 | 画布分支 | SVG 导出分支 |
|---|---|---|
| 散点 | `drawScatter()` | `buildSVG()` case `'scatter'` |
| 折线 | `drawLine()` | `buildSVG()` case `'line'` |
| 柱状 | `drawBar()` + 私有 `visibleBarRange()` | `buildSVG()` case `'bar'` |
| 直方图 | `setHistogramData()` 内联分箱 | （直方图存成柱状图，走柱状分支） |

每一处坐标都算了两遍，规则也写了两遍。其中两条规则**根本无法被测试覆盖**：
「哪些柱子落在绘图矩形内」是一个**私有方法**（`visibleBarRange`），
直方图的分箱内联在组件的 setter 里。

### 2. 热力图：屏幕上的图和导出的图**不是同一张图**（真缺陷）

| | 画布 `drawHeatmap()` | 导出 `buildSVG()` case `'heatmap'` |
|---|---|---|
| 格子宽度 | `pw / nCols`（绘图矩形均分） | `\|mapX(1) − mapX(0)\|`（视口格距） |
| 格子位置 | `margin.left + j·cellW` | `min(mapX(c), mapX(c+1))` |
| 行序 | 行 0 在**顶** | 行 0 在**底**（视口 Y 轴是反的） |
| 配色 | `floor`，绿通道封顶 100：蓝 → 灰紫 → 红（发散色阶） | `round`，蓝通道固定 255：青 → 白（顺序色阶） |

视口给数据范围加了 10 % 的 padding，所以视口格距比绘图矩形**更宽**。
4×4 矩阵、800×600 画布下的实测：

- 画布的格子：`x = 70`，宽 `172.5` → 最后一列右边缘正好 `760`（绘图矩形右边缘）；
- 导出的格子：`x = 127.5`，宽 `191.67` → 最后一列右边缘 `894.17`，
  **超出绘图矩形右边缘 134.17 px**，画到了右边距上；
- 两者的行序相反，导出的矩阵是**上下颠倒**的；
- 两者的配色公式不同，导出的图是另一套色阶。

这与 2026-10-19 修掉的箱线图缺陷是**同一类**：屏幕上的图和导出的图不是同一张图。
**这一项不是零变化**——它修的是一处真实的不一致。

### 3. EPS 导出：散点几何的第三份拷贝

`buildEPS()` 自己调 `this.mapX()` / `this.mapY()` 算散点坐标（另外还带
PostScript 的 Y 轴翻转），既不是画布那一套，也不是 SVG 那一套。

## 根因

同一逻辑存在多份实现：画布分支、`buildSVG()` 分支、EPS 分支各自算各自的坐标、
各写各的四舍五入。箱线图已经按「抽成纯函数 + 两侧共用」的模式修过一遍，
这次把剩下的图按同一模式收口。

## 修复

| 文件 | 旧行为 → 新行为 |
|---|---|
| `ets/components/plot/plotGeometry.ts`（**新增，纯 TS**） | 散点/折线/直方图/柱状图/热力图几何的唯一实现：点的像素位置、零线判定、可见柱区间、柱宽、零基线、柱矩形、分箱、分类轴范围、格子矩形与格子配色、调色板槽位 |
| `PlotCanvas.ets` | `drawScatter()` / `drawLine()` / `drawBar()` / `drawHeatmap()` / `buildSVG()` 的四个分支、`setHistogramData()`、`updateRanges()`、`buildEPS()` 改为调用共享模块；删除私有 `visibleBarRange()` |

### 热力图「以哪边为准」：**以画布为准**（导出器向屏幕看齐）

判据不是「哪边更常用」，而是**哪一边算出来的图是自洽的**：

1. **只有画布那一套能把整张网格放进绘图矩形**。视口格距让最后一列跑出绘图矩形
   134 px，压在右边距上（画布不裁剪；导出图也会越界）。
2. **只有画布那一套保持矩阵的表格式行序**（行 0 在顶）。视口的 Y 轴是反的，
   按视口摆格子会把矩阵上下颠倒。
3. **画布那一套的色阶是对的**：蓝 → 灰紫 → 红，中点中性，两端够暗够亮；
   导出器那套是青 → 白，既没有中性中点，也永远不会变暗。
4. **箱线图的先例可以套用，但结论相反**：那次画布是**客观错**的（偶数样本取上中位数、
   须线用 min/max、Y 公式绕过视口），所以改成导出器那一套；热力图的画布**不客观错**，
   它是一套自洽的设计，导出器那套反而产出了一张跑出绘图矩形的图。

代价与后果（如果上层要换成视口格距，只需改 `computeHeatmapPrimitives` 一处）：
- 视口格距 = 格子与轴刻度对齐（但热力图的轴刻度是 5 等分数值，对分类矩阵没有意义）；
- 视口格距 = 格子随缩放/平移移动（**画布那一套没有这个性质**，见「风险」）；
- 视口格距 = 行 0 在底、网格越界。

### 行为变化范围

- **散点 / 折线 / 直方图 / 柱状图 / EPS：行为零变化**（逐位对拍，见下）。
- **热力图：屏幕上的图逐位不变**（格子位置、行序、配色都保持画布原样），
  **导出出去的图变了**——格子位置与大小、行序、配色改成与屏幕一致。
  这正是本项要修的东西。

## 风险

- **画布与导出图在「呈现」上仍然不同——这是保留的旧行为，不是新缺陷**：
  导出图不画散点零线、折线不画顶点圆点、散点/折线固定 `r=5` / `opacity=0.7`、
  热力图没有行/列标签、没有数值标注、没有色条。本次统一**几何**与**配色**，
  不统一**画哪些元素**。
- **热力图的格子不随缩放/平移变化**（画布本来就是如此，本次保留）。
  要让它随动，得把热力图自己的轴范围从「列/行序号」改成「格子边界」
  （`[−0.5, n−0.5]`），并接受行序随视口 Y 轴翻转——那是**产品决策**，
  本次没有替你拍板，也没有改。
- **标记半径与透明度没有抽成共享几何**：画布的批量路径（n > 1000）与逐点路径
  对「选中点」的透明度处理本就不同（0.7 vs 0.9 / 1.0），抽成一份会改变渲染结果。
- 空折线序列在导出时仍产出 `M NaN NaN`（旧行为，已显式保留并加注释）。
- **热力图路径与 EPS 导出路径当前都不可达**：`setHeatmapData()` 与 `exportEPS()`
  在 `ets/` 里没有任何调用者（`ingestInputData()` 遇到 `'heatmap'` 直接清屏，
  工具栏只有 PNG / SVG 两个按钮）。所以本次修复**不会改变任何当前屏幕上的东西**，
  它消除的是一处一旦接线就会带病上线的缺陷。
- ArkUI 框架行为无法在 Node 验证：Canvas / SVG / EPS 的实际出图仍需实机确认。
- `docs/changes/README.md` 的索引行**未更新**——该文件不在本次改动范围内，
  由会话负责人统一补。
